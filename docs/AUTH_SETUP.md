# Подключение регистрации · Sprint 02

Supabase — выбранный в ТЗ сервис PostgreSQL, Auth и Storage. Приложение работает через сервер Next.js. Статический `dist/` остаётся отдельным демо и не запускает API.

## Локальный запуск

1. Установить Node.js 22+ и выполнить `npm ci`.
2. Скопировать `.env.example` в `.env.local`.
3. Создать проект в Supabase Dashboard. Вставить URL проекта в `SUPABASE_URL`, publishable key — в `SUPABASE_PUBLISHABLE_KEY`. Сервисный ключ `service_role` приложению не нужен; не добавлять его в браузер или Git.
4. Выполнить `supabase/migrations/202610300001_auth.sql` в SQL Editor нового проекта или через Supabase CLI. Миграция рассчитана на новую базу; существующие пользователи требуют отдельного backfill профилей.
5. В Authentication включить Email provider и **Confirm email**, установить минимальную длину пароля 12. JWT expiry — 3600 секунд. Для абсолютного срока сессии 7 дней настроить time-boxed sessions, если тариф это поддерживает. Cookie maxAge не заменяет серверное ограничение сессии.
6. Site URL: `http://localhost:3000`, разрешённый redirect URL: `http://localhost:3000/auth/confirm`. `APP_URL` должен совпадать с origin сайта. В production использовать только HTTPS: cookie автоматически получает Secure; на локальном HTTP Secure отключён для разработки.
7. Шаблон Confirm signup: ссылка `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`. TTL подтверждения — 86400 секунд. Сервер принимает только type=email, не recovery. После подтверждения требуется обычный вход.
8. Настроить SMTP для писем реальным пользователям и проверить ограничения провайдера. Встроенная отправка Supabase имеет ограничения. Не отключать email confirmation ради демонстрации.
9. `npm run dev`, открыть http://localhost:3000. Для production: `npm run build`, затем `npm start` на серверном хостинге Next.js. Существующий статический hosting manifest не разворачивает этот сервер.

Если окружение не заполнено, API отвечает 503 с объяснением; приложение не имитирует успешную регистрацию.

## Что реализовано

- Регистрация с серверной валидацией имени, email и пароля; нормализация email.
- Подтверждение email и повторное письмо; вход/выход через Supabase Auth.
- Только серверный SDK; HttpOnly, SameSite=Lax cookies; проверка Origin для POST; no-store для API.
- Проверка пользователя через `getUser`, подтверждения email и blocked при каждом запросе профиля/заявки.
- Профиль со студенческими правами по умолчанию, заявка преподавателя и запрет дубликатов pending.
- RLS: только собственные данные; запрет клиентских изменений ролей, blocked и статуса заявки. Пользовательский metadata не назначает роли.

## Что ещё нужно для полного DEV-01 / ARCH-01

Не выполнено: восстановление/смена пароля и отзыв всех старых сессий; смена имени/аватара; общий лимитер email/IP (5 неудачных входов за 15 минут, блокировка 15 минут); лимит повторных писем 5/час; интерфейс и аудит администрирования ролей; запрет удаления последнего администратора; отзыв teacher с изменением статусов курсов; полная схема курсов/версий/Enrollment/Attempt/Storage. Провайдерские ограничения не выдаются за точную реализацию этих требований. Cookie 7 дней не гарантирует абсолютную длительность refresh-сессии.

Миграция и реальная почта требуют прогона на проекте Supabase. До этого нельзя считать интеграцию принятой или запускать регистрацию для публичной аудитории. В коде нет ключей конкретного проекта и нет обхода подтверждения email.
